# development-workflow.md

## 1. 変更前に確認すること

コードを変更する前に以下を確認する。

1. 依頼内容の対象範囲
2. 関連ファイル
3. 既存の命名
4. 既存の設計
5. 既存の型
6. 既存の依存関係
7. `docs/spec.md` との矛盾
8. 既存APIへの影響
9. 既存テストへの影響

不明点があっても、実装に不要な質問で作業を止めない。
合理的な仮定を置いて進め、仮定を回答に明記する。

## 2. 変更中のルール

* 小さく変更する。
* 依頼された範囲だけを変更する。
* 既存の設計に合わせる。
* 1ファイルに複数責務を詰め込まない。
* UI、API呼び出し、状態管理、型定義、バリデーション、ビジネスロジックを必要に応じて分離する。
* プロンプトは用途ごとに分離し、質問項目設計用とAIインタビュー用を混在させない。
* AI設定タブの追加カスタマイズは実インタビュー用として扱い、質問設定チャットや項目提案APIの入力に載せない。
* 質問項目設計用の request/context/schema へ、実インタビュー用 `systemPrompt` を安易に追加しない。
* AI関連処理を変更するときは、`docs/architecture/agents/agent-architecture.md` の質問設計、インタビュー、暗黙知回答の責務を確認する。
* 質問設計エージェント、インタビューエージェント、暗黙知回答エージェントの責務を同じserviceやpromptに混ぜない。
* 暗黙知回答エージェントは read-only とし、DB更新や承認処理を追加しない。
* 長いプロンプト本文は可能な範囲で config / md / 専用 loader に分けて管理する。
* 不要な抽象化を追加しない。
* 未使用ライブラリを追加しない。
* 既存コードを広範囲にフォーマットしない。
* 命名変更やディレクトリ移動は、依頼された場合のみ行う。
* 実装中の変更仕様は`specs/<id>/`に置き、実装完了時に恒久情報を`docs/`へ反映してから`specs/<id>/`を削除する。

## 3. 変更後に確認すること

変更後は可能な範囲で以下を確認する。

* 型エラーがないか
* lint違反がないか
* 既存テストが壊れていないか
* 新規ロジックに最低限のテストがあるか
* APIレスポンス型がフロントと一致しているか
* Elasticsearch index mapping と保存データが一致しているか
* CognitoユーザーIDが保存されているか
* 認証・認可漏れがないか
* AI提案が勝手に承認済みになっていないか
* ドキュメント取り込み状態と既読状態が混ざっていないか
