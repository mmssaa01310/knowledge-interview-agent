# リファクタリングガイド

## 1. 目的

生成・修正したコードに対して、外部仕様を変えずに以下を改善する。

* 可読性
* 責務分離
* 冗長性
* 重複
* ファイル分割
* テストしやすさ
* 保守性

## 2. 基本方針

* 外部仕様を変えない。
* 依頼範囲外の大規模リファクタリングはしない。
* 小さく安全に変更する。
* 既存の設計・命名・フォルダ構成に合わせる。
* 不要な抽象化を追加しない。
* 偶然似ているだけのコードを無理に共通化しない。

## 3. ファイル分割の観点

以下が混ざっている場合は分離を検討する。

* UI表示
* API呼び出し
* 状態管理
* バリデーション
* 型定義
* 業務ロジック
* 外部サービス呼び出し
* PostgreSQLクエリ
* Bedrock呼び出し

ただし、単に行数だけで分割しない。
責務が分かれる場合に分割する。

## 4. Frontendの観点

Reactコンポーネントでは以下を避ける。

* 1コンポーネントに画面全体の処理を詰め込む
* JSX内に複雑な条件分岐を書く
* API呼び出しと表示ロジックを密結合する
* form定義、validation、submit処理、表示をすべて同じ場所に置く
* 型定義をコンポーネント内に大量に書く
* 現行の依存にない状態管理・データ取得ライブラリを前提にする
* API取得、画面状態、保存処理を一つのhookやComponentへ集約する

分離候補は以下。

* `components/`: 表示用コンポーネント
* `features/<feature>/hooks/`: 機能固有hooks
* `features/<feature>/api/`: API呼び出し
* `features/<feature>/types/`: 型定義
* `features/<feature>/utils/`: 機能固有の補助関数

現行WebはReact hooksと機能単位のController / APIモジュールを使用する。新しい状態管理、データ取得、Form、schemaライブラリは、必要性と依存追加の影響を確認してから導入する。

## 5. Backendの観点

FastAPIでは以下を避ける。

* routerに業務ロジックを書く
* routerにPostgreSQLクエリを書く
* routerからBedrockを直接呼ぶ
* Pydantic schemaと内部モデルを混在させる
* 認証ユーザーIDの保存を忘れる
* 認可チェックを省略する
* 例外処理を雑に握りつぶす

分離方針は以下。

* `routers/`: HTTP入出力、認証済みユーザー取得、service呼び出し
* `schemas/`: request / response schema
* `services/`: ユースケース、業務ルール
* `repositories/`: PostgreSQLアクセス
* `core/`: 認証、設定、共通処理

## 6. 可読性の観点

以下を改善する。

* 長すぎる関数
* 深すぎるネスト
* 複雑な条件式
* 意味が分からない変数名
* booleanフラグだらけの分岐
* マジックナンバー
* マジック文字列
* 同じような処理の繰り返し
* 何をしているか分かりにくいコメント

推奨する改善。

* guard clause / early return を使う
* 複雑な条件式は中間変数に分ける
* 意味のある単位で関数分割する
* 定数化する
* 命名で意図を表す
* コメントは「何をしているか」ではなく「なぜ必要か」を書く

## 7. 重複排除の観点

共通化してよいもの。

* 同じ業務ルール
* 同じAPI呼び出し
* 同じバリデーション
* 同じPostgreSQLクエリ生成
* 同じエラーハンドリング
* 同じ日付・状態変換

無理に共通化しないもの。

* たまたま形が似ているだけのUI
* 将来分岐しそうな業務処理
* 1回しか使われていない処理
* 共通化によって読みにくくなる処理

## 8. チェックリスト

リファクタリング後に以下を確認する。

* 外部仕様が変わっていないか
* ファイル責務が明確か
* 1ファイルに詰め込みすぎていないか
* router / service / repository の責務が混ざっていないか
* UIとデータ取得が密結合していないか
* 重複が減っているか
* 過剰な抽象化が増えていないか
* 型エラーがないか
* 既存テストが壊れていないか
* 新規ロジックに最低限のテストがあるか
