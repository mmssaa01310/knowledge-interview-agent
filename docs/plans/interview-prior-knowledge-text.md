# 事前知識のテキスト／Markdown入力への移行計画

状態: 未実装。今回の変更は仕様・計画のみ。

振る舞いの正本は[プロダクト仕様](../spec.md)の4章・7.3.3。以下は実装順序であり、現行コードの対応完了を意味しない。

## 現状と変更対象

| 対象 | 現状 | 変更方針 |
|---|---|---|
| `app/web/src/pages/KnowledgeSettingsPage.tsx`、`KnowledgeDocumentsPage.tsx` | 事前知識タブにファイル選択、アップロード、本文表示、削除 | 既知情報／専門用語の本文入力・編集・保存へ変更。ファイル選択は撤去 |
| `app/api/src/ai_interviewer_api/routers/documents.py` | JSON登録はメタデータとWorker投入、`documents/upload`はファイル本文処理 | 既存の認可・CRUDを再利用して直接本文を保存・更新。メタデータだけの成功を本文保存成功と扱わない |
| `services/document_ingestion.py`、`repositories/document_knowledge.py`（API配下） | ファイル抽出、チャンク化、PostgreSQL／Elasticsearch保存 | 本文検証からチャンク化・保存へ接続。Repositoryを再利用しファイル抽出依存を分離 |
| `services/question_design_retrieval.py`、`services/interview_document_retrieval.py`（API配下） | 文書・チャンクを検索して質問コンテキストへ渡す | 登録済み設定コンテキストと追加検索を区別し、出典・改訂を保証 |
| `agents/interview_knowledge/`（API配下） | 回答解釈・質問生成・整理 | 質問生成だけでなくInterpreterと整理にも同じ既知情報・用語を提供 |
| `services/live_interview.py`の`build_live_interview_context`（API配下） | 質問リスト、現在の質問、回答状態を組み立てる | GPT-Live初期コンテキストにも知識を追加。非同期回答整理との参照版を一致させる |
| `packages/shared-types`、APIモデル・Schema、WebのAPIクライアント・翻訳・テスト | ファイル文書の契約 | 本文形式・種別・改訂・保存結果の契約を揃える |

## 実装順序

### 1. 保存契約と移行

* 既存DocumentのID、Knowledge・テナントとの紐付け、登録者を維持できる形で本文登録・更新契約を設計する。本文形式、種別、改訂、更新競合検知を追加する。
* PostgreSQL／Elasticsearchの両Repositoryで更新・削除と古いチャンクの無効化を検証する。検索保存失敗を成功扱いせず、本文を失わず再試行できるようにする。
* 既存の抽出済み本文を直接入力項目へ移す。元タイトル・ID・出典を保ち、種別未設定は管理者が確認できるようにする。抽出失敗・本文なしは要対応として提示し、ファイル再取り込みを要求しない。
* 移行は件数・本文・出典を照合し、再実行可能にする。既存データや元ファイルを自動削除しない。バックアップ・ロールバック方法を実装時に検証する。

### 2. 設定画面

* タイトル、既知情報／専門用語、テキスト／Markdown、複数行本文の入力欄を設ける。追加・編集・削除・本文確認を提供する。
* 個別保存、保存中・失敗・検索反映状態、空本文・上限超過、未保存離脱を扱う。Markdownを表示する場合は既存の安全な表示処理を再利用する。
* ファイル入力、ドラッグ＆ドロップ、対応拡張子の案内を撤去する。管理者以外に編集操作を表示せず、API側の権限検証も維持する。

### 3. 質問と回答解釈への接続

* APIに共通の事前知識コンテキスト組み立てを置き、質問設計、次質問生成、回答解釈、非同期整理へ渡す。LLMに検索・DB権限を与えない。
* 一般的な前提の聞き直しを避ける判断と、必須回答の確認を分離する。意味判断はAIが行い、Backendは出典、対象項目、確認状態を保証する。キーワード辞書による質問スキップは追加しない。
* 設定コンテキストは`retrievalPolicy=never`でも利用し、追加検索は禁止する。既存の候補検証が検索結果だけに依存する箇所も変更する。
* 用語の解釈に原文と登録内容を併用し、不明・多義語・矛盾は確認する。発言や共有設定を勝手に書き換えない。
* コンテキスト上限、関連範囲の選択、参照改訂を扱う。開始後の設定変更は次回開始へ適用し、削除・無効化時に古い参照を続けない。音声セッションへの反映に再接続が必要なら利用者へ通知する。

### 4. 音声経路と旧経路の整理

* Transcribe + PollyとNova Sonic 2はAPIの共通質問・解釈経路を確認する。GPT-Liveは初期会話コンテキストと非同期整理の両方を確認する。
* `app/voice`へRAG・評価を複製しない。既存の全二重会話、割り込み、整理の非同期処理を維持し、新たなLLM完了待ちを会話経路に追加しない。
* 移行後はファイルアップロードAPI・Workerのファイル抽出経路を廃止対象にする。他用途の呼び出しがないことを確認して削除し、未対応形式を黙って受理しない。
* PDF／Office抽出ライブラリは全参照を確認して不要なものだけ削除し、uv lockを更新する。別用途のCSV処理などは削除しない。

### 5. 検証とドキュメント確定

| 観点 | 受け入れ条件 |
|---|---|
| CRUD | テキスト／Markdownが改行を含めて保存・再編集でき、失敗・競合時に未保存本文を失わない |
| ファイル非対応 | PDF / DOCX / XLSX / PPTX / CSVとTXT / MDのファイル登録導線がない |
| 既知情報 | 既知の一般前提は聞き直さず、未知部分・差分へ進む |
| 必須回答 | 登録内容だけで確認済みにせず、必要な短い確認後に正規状態を更新する |
| 用語 | 略称を登録内容で解釈し、曖昧・矛盾する場合は確認する。原文を保持する |
| 訂正 | 対象者の訂正を記録へ反映し、共有事前知識を自動変更しない |
| 参照制御 | `never`でも設定知識を使い、追加検索は実行しない。別テナント・Knowledgeの内容が混入しない |
| 更新・削除 | 古いチャンクの検索利用を防止し、参照版を追跡できる。両Repositoryで確認する |
| セキュリティ | 非管理者の更新、越境参照、本文の命令注入、Markdown経由のスクリプト実行を防ぐ |
| 経路差 | テキストと3音声構成で同じ用語・前提を利用し、音声と非同期整理の双方へ渡る |
| 回帰 | 未登録でも開始でき、追加質問・全項目確認・インタビュー完了・DB保存が継続する |
| 性能 | 変更前後の開始時間・応答時間を測り、整理完了を待つ直列化がないことを確認する |

API・Repository単体テスト、LLM入力契約テスト、Web操作テスト、実モデルでの会話確認を分けて実施する。型チェック・lint・関連テストを実行し、実通信を行わない検証を音声動作確認済みとは報告しない。

実装完了時は`reference/current-implementation.md`、API・エージェント・音声の関連資料を実装に合わせて更新する。仕様を各資料へ重複転記せず、正本へリンクする。
