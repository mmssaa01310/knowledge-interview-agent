## 1. 目的と前提

この文書は、ナレッジ分析と教育支援を段階的に実装するための計画である。確定したプロダクト上の振る舞いは`docs/spec.md`を正本とし、本計画は実装済みの機能を示さない。実装済みの内容は`docs/reference/current-implementation.md`を参照する。

実装では、記録のレビュー優先付けと教育支援を、人事評価や対象者のランキングに使用しない。AIによる状態候補と指導案は常に下書きとし、人による確認・公開を経て対象者へ表示する。

## 2. 実装の全体像

```text
InterviewRecord / InterviewState / ProcessState / RequirementState
                         │
                         ▼
              Backend aggregation and validation
              ├─ dashboard metrics
              ├─ review priority + evidence
              └─ learning-objective status
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
    Knowledge analysis      AI guidance drafts
           │                         │
           │                         ▼
           │              Human review / publication
           ▼
    Cross-record learning support draft
           │
           ▼
       Respondent-specific advice draft
           │
           ▼
       Human review
                                     │
                                     ▼
                     Learner's own record guidance
```

既存の`InterviewRecord`を対象者用と管理用に複製しない。集計、確認優先度、教育支援案は既存記録と質問項目・要求・プロセス要素のIDを参照する。

## 3. フェーズ0: 定義と既存データの監査

1. 既存の`InterviewRecord`、`InterviewState`、質問項目、`RequirementState`、`ProcessState`、提案、承認履歴、監査ログを確認する。
2. ナレッジごとに教育目標へ紐付ける対象を決める。初期版では既存の質問項目、要求項目、プロセス要素だけを教育目標の根拠に使う。
3. 指標の定義を固定する。記録数、提出数、承認数、対象者別の活動量、確認優先度、教育目標状態の算出範囲・期間・タイムゾーンを文書化する。
4. 個人情報、会話本文、音声原本を集計画面へ直接表示しないこと、対象者への公開前に人が確認することを確認する。
5. `admin`と`knowledge_manager`のテナント内閲覧、`knowledge_manager`の管理対象ナレッジ内公開、`interviewer`の自分の公開済み案閲覧を、認可マトリクスとして確定する。

完了条件:

* 計算に利用する保存済みデータと、利用しないデータが一覧化されている。
* 回答長・発話回数・質問回数・利用頻度だけでは確認優先度を計算しないことがテスト条件として定義されている。
* 現行の認可・記録状態遷移を変更せずに追加できる範囲と、変更が必要な点が分離されている。

## 4. フェーズ1: 集計・教育支援のドメインモデル

次の概念を、既存のドメインモデルと責務が重複しない形で追加する。

| 概念 | 目的 | 必須内容 |
|---|---|---|
| `DashboardFilter` | 集計範囲を固定する | 期間、ナレッジ、用途、記録状態、タイムゾーン |
| `RecordReviewPriority` | 確認する順序を示す | `low`/`medium`/`high`、根拠、計算日時、入力版 |
| `LearningObjective` | 確認・学習する単位を定義する | 対象ナレッジ、参照する質問・要求・プロセス要素、期待内容 |
| `LearningEvidence` | 状態判断の根拠を保存する | 記録ID、メッセージIDまたは構造化要素ID、参照箇所 |
| `LearningAssessment` | 教育目標ごとの記録上の状態 | 仕様に定めた状態、根拠、計算日時、入力版 |
| `GuidanceDraft` | AIまたは管理者が作る支援案 | 学習案内、指導案、再確認質問、下書き状態 |
| `GuidancePublication` | 対象者に見せる内容を管理する | 公開状態、公開者、公開日時、対象者、案の版 |

確認優先度の計算はBackendに実装し、各結果に根拠を必須とする。数値スコアを内部利用する場合も、対象者の順位や能力値として保存・表示しない。画面には`low`、`medium`、`high`と理由を表示する。

完了条件:

* 同じ入力版では同じ優先度と根拠が再現される。
* 根拠が存在しない優先度・教育状態を保存できない。
* `not_evidenced`が「理解していない」という意味にならない文言と型定義になっている。

## 5. フェーズ2: Backend集計・認可API

1. `admin`と`knowledge_manager`が利用できるテナント内集計APIを追加する。レスポンスには集計値、確認優先度、理由、既存記録への識別子だけを含める。
2. 記録の詳細、会話、根拠の本文は既存のナレッジ配下記録APIで取得する。横断集計APIで本文を返さない。
3. 教育目標、教育状態、下書き、公開状態を取得・更新するAPIを追加する。
4. 公開・非公開・編集は`admin`または対象ナレッジを管理する`knowledge_manager`だけに許可する。
5. 対象者向けAPIは、本人の担当記録に対する公開済み案だけを返す。
6. すべての更新でテナント、ロール、記録担当、記録状態、対象ナレッジの管理権限を検証し、監査ログを保存する。

完了条件:

* `interviewer`、`viewer`、権限外の`knowledge_manager`が横断集計や他者の教育支援案を取得できない。
* URLやAPIを直接呼び出しても、記録本文・教育支援案の認可を回避できない。
* 公開前の案は対象者向けレスポンスに含まれない。

## 6. フェーズ3: ナレッジ分析UI

1. ナレッジ一覧画面のヘッダーに、`admin`と`knowledge_manager`だけが見える「ナレッジ分析」入口を置く。内部ルートは`/dashboard`とし、左サイドバーの構造は変更しない。
2. 期間、ナレッジ、用途、記録状態を絞り込めるようにする。表示・集計はログインユーザーの`timezone`、文言と数値書式は`uiLocale`を使用する。
3. フィルター直下に「分析」「学習支援」タブを置く。「分析」タブへ概要カード、時系列、ナレッジ別の状況、活動量、確認優先度一覧を表示し、「学習支援」タブへ複数記録の学習支援分析を表示する。活動量に順位や理解度を示す色・名称を使わない。
4. 確認優先度一覧には、段階だけでなく根拠と既存記録詳細への導線を表示する。
5. 空状態、読込中、権限不足、取得失敗、長いナレッジ名・対象者名、モバイル表示を実装する。
6. 回答者ごとに記録数、回答数、提出数、教育目標の状態別件数を表示する。表示は運用状況の集計に限定し、順位を付けない。
7. 確認対象の記録は、折りたたみ可能な1行リストとスクロール領域で表示する。
8. 個別記録の教育支援案はナレッジ分析画面へ表示せず、既存の記録単位の公開済み学習案内機能を維持する。

完了条件:

* 管理者は、本文を集計画面に露出させずに確認対象と理由を把握できる。
* すべての集計表示はフィルターと期間に一致する。
* 現在の「記録はナレッジ配下で扱う」ナビゲーション原則を崩さない。

## 7. フェーズ4: AI支援案と指導者レビュー

1. 構造化出力で、教育状態候補、根拠候補、追加確認質問、学習案内、指導案を生成する。
2. LLM入力は対象記録の認可済み会話、確定済み構造化状態、対象教育目標に限定する。
3. Backendで根拠ID、対象教育目標、記録版を検証し、検証できない候補は破棄する。
4. 指導者画面で、根拠を確認しながら案を編集、公開、非公開にできるようにする。
5. AIモデル、入力版、生成日時、生成者、公開者を監査する。

完了条件:

* AI生成だけで対象者へ案が公開されない。
* 指導者は各案がどの質問・回答・構造化要素に基づくか確認できる。
* AIが根拠のない理解不足・能力評価を作成しても保存・公開されない。

## 8. フェーズ5: 対象者向け学習案内と再確認

1. 対象者が自分の担当記録で、公開済みの「確認できた内容」「次に確認・学習する内容」「推奨する演習」「再確認質問」を確認できるようにする。
2. 未公開の案、管理者向けの確認優先度、他者の情報を対象者画面に表示しない。
3. 再確認は既存の記録作成・インタビュー状態遷移を再利用し、教育目標と元の公開案への参照だけを追加する。
4. 再確認後は、同一教育目標について根拠と状態の変化を表示する。対象者間の比較は追加しない。

完了条件:

* 対象者は、自分が次に何を確認・学習すべきかを公開済み情報だけで理解できる。
* 再確認によって既存の記録状態遷移や正式承認フローを迂回しない。

## 9. フェーズ6: 評価、運用、段階展開

1. 実データを匿名化した評価セットで、優先度の根拠、教育状態、指導案の妥当性を指導者が評価する。
2. 「確認対象であるが問題なし」「根拠不足」「有用な指導案」の区別を測定し、優先度ルールとプロンプトを改善する。
3. 集計対象件数が増えた場合に、集計時間、ページネーション、キャッシュ、更新頻度を測定する。新しいDBやAWSサービスは、この測定結果と承認なしに追加しない。
4. 監査ログ、公開履歴、アクセスログを運用手順に組み込み、誤公開時の非公開・訂正手順を確認する。
5. 画面文言、空状態、エラー、説明を`ja-JP`、`en-US`、`zh-CN`、`th-TH`で追加し、翻訳整合性検査に含める。

## 10. 共通の検証項目

* Backendの認可テスト: 各ロール、他テナント、他者記録、公開前後、URL直接アクセス。
* 集計テスト: 期間、タイムゾーン、ナレッジ、用途、記録状態の各フィルターと合計値。
* 優先度テスト: 根拠付き信号だけで計算され、回答量・利用頻度だけでは優先度が上がらないこと。
* AI契約テスト: 根拠IDの不足・不一致、入力版競合、根拠のない候補、公開前案の遮断。
* 学習支援分析テスト: 同一ナレッジの2件以上だけを対象にし、全体分析の後に回答者別分析を実行する。教育目標状態の件数はBackend計算値を使い、AIのID参照と回答者ごとの記録分離を検証する。生成結果は下書きであり、確認済み化を経ても対象者へ自動公開しない。
* 状態遷移テスト: 記録状態と教育状態を混同せず、承認済み記録の既存制約を維持すること。
* Frontendテスト: loading、empty、error、長文、狭い画面、キーボード操作、visible focus、4言語でのレイアウト。
* 既存のFrontend build/typecheck/test、Backend lint/typecheck/test、必要な統合テストを実行する。

## 11. 初期実装の対象外

* 個人の理解度・能力・成績を数値化または順位付けする機能
* AIだけによる記録承認、差し戻し、教育支援案の公開
* 本文・音声原本を横断ダッシュボードへ表示する機能
* `interviewer`と`viewer`へのテナント横断集計の提供
* 承認なしの新規DB、AWSサービス、外部人事システム連携
